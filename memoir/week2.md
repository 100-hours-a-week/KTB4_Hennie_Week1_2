# 최종 추가 구현 사항

- 여러 사용자 스레드(언니, 동생) 개념을 추가해 비동기 프로그램으로 제작했다.
    - 한 사용자의 추천 요청을 받아 run() 메서드 안에서 `recommendOutfit()`을 호출하고, 추천 결과를 출력하도록 했다.
    - 사용자가 입력한 값은 `UserRequest` 클래스로 분리했다. 언니와 동생 각각의 요청을 독립적으로 관리한다.
- 이번 구현에서 가장 중요한 공유 자원은 `ClothingCatalog`에 있는 옷 객체들이었다. 언니와 동생 스레드가 같은 옷 객체에 접근할 수 있기 때문에, 옷을 추천하고 점유하는 과정에서 동시성 문제가 발생할 수 있었다.

  `ClothingItem`에 옷 상태를 `enum`으로 추가했다. `CLEAN`(착용 가능한 상태) / `IN_LAUNDRY`(빨래 바구니에 있어 착용이 불가능한 상태)로 관리하고, 실제 착용 가능 여부는 상태가 `CLEAN`이면서 어떠한 사용자도 착용하고 있지 않은지 그리고 `Optional`로 판단했다.

- 추천 로직에서 `recommendOutfit()` 메서드를 `synchronized`를 적용해 한 사용자의 전체 코디 추천이 끝나기 전까지 다른 스레드가 추천 로직에 들어가지 못하도록 했다.

  ⇒ 상의, 하의, 아우터, 신발 추천을 이전처럼 따로 동기적으로 진행하다보면, 상의만 언니가 가져가고 하의는 동생이 가져가는 흐름으로 추천한 코디가 각각 다른 사용자에게 갈 수 있는 상황을 예방했다.


### 추가사항

아래의 사항들을 구현하지 못해서, 아쉬운 조건들:

- 언니랑 동생이랑 같은 조건으로 검색했을 때, 다른 사용자로 인해 못 입은거면, 다른 사용자가 착용중입니다. 출력
- 빨래통 관련 옷 상태를 활용하지 못한게 아쉽다. 추후에 빨래를 하는 세탁기 관련 스레드도 추가해보면 좋을 것 같다.

  사실은 옷 착용 횟수와 함께 연관지어서 추가를 하려고 했지만, 예상보다 여기까지 구현하느라 시간이 오래 걸려서 구현해내지 못했다.

    ```
    - 빨래 바구니 상태 확인: 대기 상태 중인 빨래감이 있는지 확인하고, 최대 용량을 넘지 않도록 대기 중인 빨래감 → 빨래 바구니로 이동함. (대기 상태 중인 빨래감에도 최대 용량 설정하고, 넘치면 빨래부터 하세요! 출력)    
    - 빨래 바구니에서 옷을 꺼냄. 이때, 종류별로 진행하되, 뭐부터 할지는 랜덤.    
    - 세탁 진행 중 메세지 출력
    - 세탁 완료 후 옷 상태 업데이트
    ```

  ⇒ 이렇게 했을 때 충돌 가능성이나 잘못 설계했다고 생각되는 지점이 있는지 궁금하다.


# 2주차 회고록

- 언니와 동생이라는 사용자 스레드 작업도 명확하게 분리했다.

  `UserRecommendationTaskf`라는 클래스에서 사용자의 추천 요청을 받아 run() 메서드 안에서 추천을 실행하고 결과를 출력한다. 사용자의 입력 정보는 `UserRequest` 클래스로 분리해 사용자, 날씨, 스타일을 함께 관리하도록 했다.

  이번 작업을 하면서 패키지 구조에 대한 고민도 생겼다. User는 사용자 자체를 표현하는 도메인 개념이기 때문에 user 패키지에 두는 것이 자연스럽지만, `UserRequest`와 `UserRecommendationTask`는 사용자와 관련은 있지만 실제로는 콘솔 앱의 입력 흐름과 스레드 실행 작업에 더 가까운 클래스라고 느껴졌다. 이런 클래스들을 user 패키지에 두는 것이 맞는지, 아니면 app 패키지로 옮기는 것이 더 적절한지 아직 고민이 남아있다.

- 처음에는 언니와 동생이라는 두 사용자(스레드)들에게 각각 추천을 하도록 동기화 보장을 해주면 된다고 생각했다. 그러다보니 상의, 하의, 아우터, 신발을 추천하고 출력하는 과정에서 하나의 outfit을 추천할 때, 언니한테 해당 outfit의 상의를 추천하고 동생에게 해당 outfit의 하의를 추천하는 문제가 발생했다.

  그래서 두 사용자가 동시에 같은 옷을 추천받지 않도록 막는 것과 추천된 결과의 전체 결과물인 outfit을 추천을 요청한 사용자에게 그대로 줄 수 있도록 수정했다.

- 그리고 동시성 처리에서는 `volatile`과 `synchronized`의 차이를 고민했다. 처음에는 옷 상태를 여러 스레드가 바로 확인할 수 있도록 `volatile`을 사용하면 될 것 같다고 생각했다. 하지만 `volatile`은 변경된 값을 다른 스레드에게 보이게 해주는 역할일 뿐 “확인하고 변경하는 작업”을 하나로 묶어주지는 못한다는 것을 알게 되었다.

  이 프로그램에서는 두 사용자가 동시에 같은 옷을 보고 입으려고 할 수 있으므로, `tryWear()` 메서드에 `synchronized`를 적용해 착용 가능 여부 확인과 점유를 한 번에 처리하도록 했다.

- 참고로 lock까지 추가하지 못했던 이유는 현재 프로그램의 상황이 조금 단순해서였다. 공유 자원이 옷 객체와 출력 흐름 정도로 제한되어 있고, 사용자도 언니와 동생 두 명만 존재하기 때문에 별도의 Lock 객체를 도입하기보다는 synchronized만으로도 필요한 동시성 제어를 처리할 수 있다고 판단했다.

  그래서 tryWear()에서는 한 옷에 대해 착용 가능 여부를 확인하고 착용자를 등록하는 작업만 보호하면 되었고, recommendOutfit()에서는 한 사용자의 전체 코디 추천이 끝날 때까지 다른 스레드가 들어오지 못하게 막으면 되었다.

  시간이 된다면, 조금 더 복잡한 조건들을 추가해 Lock 개념까지 적용해보고싶다.

- 이전 과제의 피드백이었던 null을 사용하지 않고 `Optional.empty()`와 `Optional.of(user)`를 사용해 착용자가 없는 상태와 있는 상태를 표현했다. 이를 통해 옷이 깨끗한 상태인지, 누군가 입고 있는지(현재 착용자는 `Optional<User>`로 따로 관리), 빨래 바구니에 있는지를 더 명확하게 구분할 수 있었다.
- 이번 과제를 통해 스레드는 공유 자원을 어떻게 안전하게 다룰지와 연관된다는 점을 다시 한 번 깨닫게 되었다.

# 질문사항:

- 현재 옷 추천 프로그램을 비동기 구조로 바꾸면서 User, UserRequest, UserRecommendationTask 클래스를 추가했습니다.

  User는 언니/동생이라는 사용자 자체를 표현하는 enum이고,
  UserRequest는 사용자의 날씨/스타일 입력값을 담는 클래스이며, UserRecommendationTask는 Runnable을 구현해서 사용자별 추천 작업을 스레드로 실행하는 클래스입니다.

  처음에는 이 세 클래스를 모두 user 패키지에 두었는데, UserRequest와 UserRecommendationTask는 순수한 사용자 모델이라기보다 콘솔 앱의 실행 흐름과
  스레드 작업에 더 가까운 것 같아 app 패키지에 두는 것이 맞는지도 고민됩니다.

  이런 경우 패키지를 역할 기준으로 나눌 때,
  user 패키지에는 User enum만 두고 UserRequest, UserRecommendationTask는 app 패키지로 옮기는 것이 더 적절할까요?

  아니면 사용자와 관련된 입력 요청, 사용자 스레드 작업까지 user 패키지에서 함께 관리하는 것이 더 나은 구조일까요?

  패키지를 나눌 때 어떤 기준으로 우선적으로 봐야 하는지 조언을 받고 싶습니다.
